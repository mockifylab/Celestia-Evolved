## Confirmed root causes (from source inspection)

### Updater / version registration (spec §3)
- `services/Updater.qml`: `currentVersion = env || CUtils.version`, where
  `CUtils.version()` returns the string **compiled into libcaelestia-core.so**
  at build time (`QStringLiteral(CAELESTIA_VERSION)`).
- `assets/update/apply_update.sh cmd_apply`: backs up, rsyncs staged→install,
  records rollback coordinates — but **records no installed version anywhere**,
  and the release tarball carries no `VERSION` metadata (release.yml embeds a
  `REVISION` sha only).
- Consequence: after applying an update and restarting, `currentVersion` still
  reports the pre-update compiled value, so the same release is re-offered and
  About/Updates show a stale installed version. The user's own v1.0.1 self-
  update exhibits exactly this (spec confirms "does not correctly register the
  updated version").
- Fix direction (staged, testable, matches packaging model): authoritative
  installed-version metadata file in the install dir, written by `apply` and
  read by Updater BEFORE falling back to the compiled constant. Also: C++
  plugin changes cannot reach users through a source-tarball update — must be
  documented honestly and version metadata must not depend on rebuilt C++.
