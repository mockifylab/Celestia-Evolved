## Confirmed root causes (from source inspection)

### Updater / version registration (spec §3)
- `services/Updater.qml`: `currentVersion = env || CUtils.version`, where
  `CUtils.version()` returns the string **compiled into libcaelestia-core.so**
  at build time (`QStringLiteral(CAELESTIA_VERSION)`).
- `assets/update/apply_update.sh cmd_apply`: backs up, rsyncs staged→install,
  records rollback coordinates — but **records no installed version anywhere**,
  and the release tarball carries no `VERSION` metadata (release.yml embeds a
  `REVISION` sha only).
- Consequence: after applying an update and restarting, `currentVersion` still
  reports the pre-update compiled value, so the same release is re-offered and
  About/Updates show a stale installed version. The user's own v1.0.1 self-
  update exhibits exactly this (spec confirms "does not correctly register the
  updated version").
- Fix direction (staged, testable, matches packaging model): authoritative
  installed-version metadata file in the install dir, written by `apply` and
  read by Updater BEFORE falling back to the compiled constant. Also: C++
  plugin changes cannot reach users through a source-tarball update — must be
  documented honestly and version metadata must not depend on rebuilt C++.

# Implementation record (what actually changed)

## §2 Sliders — commit `eea3d0f6`

Root cause was shared, not per-page: the thumb position was computed from the
raw value against a hardcoded range, the fill used a second (different) ratio,
and steps were applied by float accumulation, so displayed value, handle
position, track fill and the persisted setting disagreed.

- `utils/sliderMapping.js` (new, single source of truth): `normalize()`,
  `denormalize()`, `snapToStep()`, `fillRatio()` — range/step/unit aware, exact
  endpoint handling, no float drift (`Math.round` on the step index).
- `components/controls/StyledSlider.qml`: handle geometry now derived from the
  shared library; track fill and `value` come from the same normalized number;
  click position maps through the travelled-handle width instead of the full
  width (previously a click at the far right could not reach the maximum).
- `modules/nexus/common/SliderRow.qml`: writes the snapped value to config and
  displays the same number; reversed ranges and percent↔fraction conversions
  fixed at the row level so pages passing 0–100 percentages and pages passing
  0–1 fractions both behave correctly.
- Audited every settings slider (Motion, Appearance, Panels/Taskbar, Hyprland,
  Audio, Services) and corrected the ones with mismatched min/max/step/unit
  bindings rather than papering over them in the component.
- Regression fixture: `tests/sliders/` (`run-mapping-test.sh`) — 28 assertions.

## §3/§4 Updater — commit `f4636ba6`

- `assets/update/apply_update.sh`: on a successful apply, writes the installed
  version into `<install>/VERSION` (from the payload's `VERSION`), so the
  install itself becomes the authoritative record. Failures leave the previous
  `VERSION` untouched (rollback re-applies the old one).
- `.github/workflows/release.yml`: the release tarball now contains a `VERSION`
  file derived from the tag, so any install from a release carries metadata.
- `services/Updater.qml`: one precedence chain used by the Updates page, About
  page and the comparison logic — `CAELESTIA_UPDATE_CURRENT` (test override) →
  in-session override → installed `VERSION` file → compiled `CUtils.version`
  (legacy installs without a `VERSION` still work, just via the old value).
- `modules/nexus/pages/UpdatePage.qml`: shows the real installed version, real
  latest release, real release notes from the GitHub release body, honest state
  text (idle/checking/available/downloading/verifying/applying/done/failed),
  the download size, and buttons wired to the actual
  `Updater.check/download/install/rollback` implementation — no UI-only stub.
- Re-offer bug fixed: after a successful install the comparison uses the newly
  registered version, so the same release is no longer offered.
- **Found while testing the v1.0.2 upgrade path**: `cmd_apply` mirrors the staged
  payload with `rsync --delete`, which silently deleted anything in the install
  directory the release does not ship — including installed plugins. `plugins/`
  is now excluded (rsync excludes are also protected from deletion) in apply, in
  the failure-restore path, and in rollback; a fixture case seeds a legacy
  install with a plugin and asserts it survives both apply and rollback.
- Fixtures: `tests/updater/run-fixture.sh` (36 assertions: download failure,
  bad digest, invalid archive, interrupted apply, rollback, VERSION registered,
  legacy install with no `VERSION` → v1.0.2-shaped apply → not re-offered,
  plugins preserved) and `tests/updater/run-qml-fixture.sh` (14 assertions incl.
  "same release not re-offered after install", "apply registers new version").

## §5 Wallpaper-derived colours — this commit

The `caelestia` CLI dependency was an **incorrect assumption in the code**, not
a project dependency: `modules/nexus/pages/wallandstyle/ColourSelect.qml` gated
the whole feature behind `command -v caelestia` and reported "not installed",
while the shell already ships a real analyser. Fixed the feature instead of
adding a dependency:

- `services/Colours.qml`: extraction now goes through the compiled
  `Caelestia.Images.ImageAnalyser` (5-bit-histogram dominant colour + mean
  luminance). New state machine `extractionState` (`idle|extracting|ok|failed`)
  with honest `extractionError` for: no wallpaper, unsupported/unknown image
  format, unreadable path, and stalled/undecodable images (5 s timeout, so a
  hanging analyse cannot silently report success). Never fabricates colours:
  `applyRoles()` refuses an incomplete role set and surfaces `themeError`.
- Per-wallpaper seed cache + regeneration: switching wallpaper re-extracts; a
  previously extracted wallpaper applies instantly from cache; "Refresh"
  discards the cache entry and re-extracts.
- `services/ColorGen.qml`: single design system — HSL tonal ramps for every
  supported role plus a coherent `term0..term15` terminal ramp; optional
  `sat`/`neutralSat`/`variantSat` knobs; `isValidSeed()`; `mixHue()`.
- No C++ was rebuilt: everything runs in QML, which is required because the
  tarball updater only ever replaces shell sources, never
  `~/.local/lib/qt6/qml/Caelestia/lib/*.so`.
- Persistence: `${Paths.state}/caelestia/theme.json` (source, built-in palette
  id, wallpaper seed + path, cache). Legacy installs are migrated once: an
  external `scheme.json` maps to the `scheme` source, `colors.customEnabled`
  maps to `custom`, otherwise `wallpaper`.
- Palette sources: `builtin`, `wallpaper`, `custom` (legacy single seed),
  `scheme` (legacy external file). `IpcHandler { target: "colours" }` exposes
  `get/set/list/palette/seed/status` for scripted verification.
- Fixture: `tests/palettes/` (`run-palette-fixture.sh`) — 18 assertions.

## §6 Built-in Celestia palettes + Appearance selector — this commit

- `services/BuiltinPalettes.qml` (new singleton): four curated palettes
  (`celestia`, `dawn`, `verdant`, `nocturne`), each a seed + design-system opts,
  rendered through `ColorGen.roles(seed, light, opts)` so both dark and light
  variants are generated from the same system and every supported role is
  covered (background, surface, elevated, on-surface, muted/outline, accents,
  hover/selected states, error, terminal ramp, …). Unknown ids return an empty
  role set, which `Colours` refuses to apply instead of guessing.
- `modules/nexus/pages/AppearancePage.qml`: new "Palette source" selector
  (Built-in / From wallpaper / Custom colour / External scheme), a second row
  listing the built-in palettes (only for that source), the seed picker only
  for `custom`, and a live status row for the wallpaper source; mode switch
  routes through `Colours.setMode` so dark/light picks the matching palette.
- `modules/nexus/pages/wallandstyle/ColourSelect.qml`: CLI gate and the
  misleading "CLI not installed" notice removed; real status card (state,
  message, extracted seed), source/palette/mode selectors, and a wallpaper-only
  refresh action.
- Applied through the existing theme architecture (`Colours.current` /
  `Colours.palette`), so bar, dock, launcher, settings, panels, control centre
  and notifications follow automatically; no per-component hardcoded colours.
